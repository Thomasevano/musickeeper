# Accessibility

Before this, accessibility here was one afternoon of fixes in April 2026 and a
hope that nothing regressed. This file describes what now holds that line
automatically, what it deliberately does not hold, and what only a human can
check.

## The automated suite

`tests/e2e/a11y.spec.ts` runs [axe-core](https://github.com/dequelabs/axe-core)
through `@axe-core/playwright` against the real application, and adds keyboard
journeys that axe cannot see.

```bash
pnpm exec playwright test tests/e2e/a11y.spec.ts
```

It is part of `pnpm test:e2e`, so the PR-preview workflow already runs it on
every pull request from this repository, against the deployed preview image.
There is no separate a11y job: an accessibility failure is a failing end-to-end
suite, which is the point.

### The bar

Only `serious` and `critical` violations fail the suite. `moderate` and `minor`
findings are still reported by axe but do not gate: they are mostly
best-practice hints, and gating on them would make the suite noisy enough that
people stop reading it.

Rules are scoped to the WCAG tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`.

### What it scans

Both colour schemes, and a 390x844 phone viewport for the surfaces that change
shape there:

| Surface                                        | Why it earns a scan                                    |
| ---------------------------------------------- | ------------------------------------------------------ |
| Home page                                      | The only page that is not the list                     |
| Listen later page, empty and populated         | Empty state and table are different trees              |
| Search results, skeletons then options         | The skeleton is a distinct DOM, live for seconds       |
| Offline alert                                  | Renders only when the browser goes offline             |
| Add dialog: loading, loaded, duplicate, failed | Four states, one component                             |
| Delete confirmation dialog                     | The only destructive path                              |
| Toasts, success and error                      | Added by `c19e379`; live regions are easy to get wrong |
| Listen later cards (mobile)                    | The table becomes cards below `md`                     |
| Navigation sheet (mobile)                      | A dialog that only exists on small screens             |
| Add dialog at a phone width                    | Renders as a sheet, not the desktop dialog             |

Dialog scans are scoped to `[role="dialog"]` and additionally assert
`aria-modal="true"`. bits-ui leaves the page behind a modal in the accessibility
tree and relies on the focus scope plus `aria-modal` to keep a screen reader
inside, so scanning the whole page would measure the dimmed background against
its own overlay and report contrast failures nobody can read.

Animations are settled before every scan. Contrast is measured against whatever
is painted at that instant, and a scan fired mid-transition blends colours with
the overlay they are fading over.

### What it does not scan

The error pages. `inertia/pages/errors/not_found.svelte` and
`server_error.svelte` are AdonisJS starter stubs that nothing renders: the
exception handler declares no `statusPages`, so a missing route answers with raw
JSON and neither page is reachable. `errors_controllers.ts` is dead beside them,
unrouted and rendering an `errors/unauthorized_access` page that does not exist.
Issue #36 listed these surfaces on the assumption they existed; scanning a page
that never renders measures nothing. The three artefacts and the product
decisions they need are written up in #54.

### Keyboard journeys

- the paste-link journey completes with no mouse at all
- the add dialog traps focus, closes on `Escape`, and gives focus back
- the delete dialog closes on `Escape` and returns focus to the row menu
- arrow keys reach the search results and scroll them into view

## The allowlist

One rule is parked, in `ALLOWED_RULES`:

**`scrollable-region-focusable`** — the search results popup is a
`max-h-[300px] overflow-y-auto` region. axe sees a scrollable container with no
tabbable descendant and reports that a keyboard user cannot scroll it. That is
true of `Tab` and false of the widget: the results are a `role="listbox"` owned
by a `role="combobox"` input, and the ARIA authoring practice is precisely that
options are _not_ in the tab order — the combobox keeps focus and arrow keys
move a roving `tabindex` through the options, which scrolls them into view. The
test `arrow keys reach and scroll the search results` measures that: it presses
`ArrowDown` past the fold and asserts the region actually scrolled and the
focused option is inside the visible box.

Empty is the goal state for this list. Every entry owes an explanation here.

## Colour

Every token pair below is measured from `resources/css/app.css` as it stands.
Text needs 4.5:1 (WCAG 1.4.3); control boundaries and icons need 3:1 (1.4.11).

| Pair                                      | Needs | Light | Dark  |
| ----------------------------------------- | ----- | ----- | ----- |
| `foreground` on `background`              | 4.5   | 19.90 | 19.05 |
| `muted-foreground` on `background`        | 4.5   | 5.21  | 7.77  |
| `muted-foreground` on `muted`             | 4.5   | 4.74  | 5.81  |
| `input` border on `background`            | 3     | 3.25  | 3.56  |
| `ring` on `background`                    | 3     | 5.11  | 4.42  |
| `destructive` as text on `background`     | 4.5   | 6.46  | 6.04  |
| `destructive-foreground` on `destructive` | 4.5   | 6.18  | 5.44  |
| `warning` icon/border on `background`     | 3     | 3.29  | 7.46  |
| `warning-foreground` on `background`      | 4.5   | 12.32 | 18.45 |

Four of those were failing and moved:

- **`muted-foreground`** 46.1% -> 44%. It read 4.39:1 on `muted`, just under AA,
  and `muted` is where secondary text most often sits.
- **`input`** was the same value as `--border`, 90% light and 15.9% dark. A
  decorative edge owes nothing, but the boundary that tells you where a control
  is owes 3:1. They are now different tokens with different jobs.
- **`ring`** 64.9% -> 45% light. A focus ring at 2.56:1 is not a focus ring.
- **`destructive`** is read as text five times over and used as a fill once, so
  it became the readable ink and `destructive-foreground` answers to the fill.
  In dark mode no single red is legible on near-black _and_ takes white on top,
  so dark picks a light red for the ink and darkens the fill's label instead.

Two hardcoded Tailwind greens also moved, because they carry state:

- listened badge `text-green-600` -> `text-green-800` in light: 3.00 -> 6.49
- toast success icon `text-green-500` -> `text-green-800` in light: 2.28 -> 7.13

The dark variants (`green-400`, 8.54 and 11.42) already passed and are unchanged.
The amber alert variant now uses the `--warning` token instead of hardcoded
`amber-500`/`amber-600`, which is what that token was introduced for.

Purely decorative borders (`--border`, `--sidebar-border`) stay below 3:1
deliberately. 1.4.11 applies to boundaries that identify a control, not to
every line on the page.

## Motion

`prefers-reduced-motion: reduce` is honoured everywhere, and it means _remove
the travel, keep the fade_. Opacity carries the state change; nothing slides,
scales, or spins. A surface that vanished instead of fading would be a
regression too — the change has to stay legible.

Most of it is one block in `resources/css/app.css`. tailwindcss-animate routes
every `animate-in`/`animate-out` through `--tw-enter-*`/`--tw-exit-*` custom
properties, so neutralising those covers the dialog, sheet, dropdown, select,
tooltip and popover at once; the dialog additionally swaps its scale curve for
the overlay's, and `.animate-spin` becomes a pulse. Three surfaces cannot be
reached from CSS and guard themselves: `data_table_row_transitions.ts`,
`data-table-status-badge.svelte`, and the highlight scroll in
`listen-later.svelte`. Toast motion belongs to `svelte-sonner`, which ships its
own `prefers-reduced-motion` block.

The gate is `no surface travels once the OS asks for reduced motion`. It hooks
`animationstart`, `transitionstart` and `Element.prototype.animate` before the
page loads, walks the app under emulated `reduce`, and asserts no keyframe
carries a transform that resolves to anything but the identity matrix. Every
guard above was mutated and the gate caught each one.

Two blind spots shape how that test is written:

- **A full turn is an identity matrix at both ends.** `rotate(360deg)` resolves
  to `matrix(1, 0, 0, 1, 0, 0)`, so the spinner reads as motionless through its
  keyframes. Hence the direct `animation-name` assertion next to the loader.
- **Svelte skips a local `out:` when its parent block is destroyed.** Deleting
  the only row empties the list and takes the table with it, so the row
  transition never runs. The test seeds two rows and deletes one.

## The manual pass

**Status: not yet run.** axe finds roughly a third of accessibility defects, and
none of the ones this list is about. The following needs a person with
VoiceOver, and its findings belong in this section.

Run VoiceOver (`Cmd+F5`) on Safari, and walk:

1. **Home to list.** Is the page title announced on navigation? Inertia swaps
   the DOM without a document load, so the announcement is not free.
2. **Paste a link.** Does the dialog announce its name and describe itself on
   open? Does the duplicate state get announced when it replaces the loading
   state, or does it change silently behind the reader?
3. **Add to list.** Does the success toast reach the reader? It is
   `aria-live="polite"` inside a region named "Notifications", so it should
   arrive after the current utterance, not interrupt it.
4. **Search and arrow through results.** Are the options announced with their
   position ("2 of 12")? Is the add/remove state of each option clear from what
   is spoken, not just from the icon?
5. **The table.** Are column headers associated with cells when reading across a
   row? Is a sort change announced, and does it say which direction?
6. **Delete.** Is the confirmation dialog's question read before the buttons?
   After deleting, is anything announced at all, or does the row just vanish?

Note what is confusing rather than what is broken. Everything structural above
is already covered by the suite; what a reader cannot get is a different kind of
finding.
