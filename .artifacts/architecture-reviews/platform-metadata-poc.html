Does the abstraction earn its extra layer?

Verdict: contextual metadata makes the caller cleaner, but does not make the whole system simpler today. Reusing #67 unchanged is the weaker option.

Question#67 unchanged in the existing flowContextual-result variant
What does the caller still know? URL parsing, parsed type, original URL, error context and metadata mapping. The wrapper does not hide those requirements. One call returns metadata ready for enrichment, or an error with its original URL. Platform resolution is hidden from the caller.
Depth / leverage Low here: wraps work the caller still partly repeats. The result lacks context needed by this consumer. Better: parsing, platform fetching, error context and mapping share one interface. Only one production consumer benefits so far.
Locality Parsing appears in two modules. Changes to parse-related assumptions require checking both. Resolution changes live in the new module; enrichment/artwork/fallback policy stays in the extractor. Following the full happy path requires one extra file.
Runtime work Supported-link fixtures: two parses, one platform call. No search/request savings. Same parse, provider and search counts as the baseline. Cleaner ownership, not a performance improvement.
Testing seam Existing dependency ports already permit parser/provider substitution. Another class is not needed just to make this testable. Can exercise contextual resolution separately. Existing extraction contract still needs coverage; no new permanent tests added in this prototype.
Maintenance / review Extra module, constructor dependency and registration without removing caller knowledge. Smaller extractor, but another module, registration and interface to understand. Same behavior spread over more files.
Deletion test Deleting the wrapper removes duplicate parsing in this integration; provider calls can stay directly in the extractor. Deleting the module moves its implementation back into one caller. No demonstrated duplication across multiple production consumers is eliminated.

Decision for this project

Keep the existing flow for now. The adapters already hide provider-specific complexity, and the current extractor already composes them with enrichment. A separate contextual module is reasonable if platform resolution should be an independently owned responsibility or another real consumer needs it; neither is a demonstrated requirement here.

If choosing that separation, use the contextual interface and preserve the existing HTTP/UI contract. It is not #67 as written: its result changes, and adoption would need its callers/tests migrated. This POC does not justify shipping the unused new endpoint.

Rollback: restore extractor and provider together. No storage migration or UI contract change. Blast radius: existing link metadata extraction and dependency wiring.
